## Fachliche Klarstellung FVG

Die verbreitete „3 Bars“-Regel ist die Formationsregel, nicht die Lebensdauer:

- Bullish FVG auf Kerze i: `low[i] > high[i-2]`
- Bearish FVG auf Kerze i: `high[i] < low[i-2]`
- Die mittlere Kerze ist Kerze i-1.
- Danach bleibt jede Zone unabhängig aktiv, bis sie vollständig mitigiert ist:
  - Bullish: `low <= zone.bottom`
  - Bearish: `high >= zone.top`

Keine pauschale 3-Bar-Ablaufzeit. Keine aktive, unmitigierte Zone allein wegen eines Array-Limits entfernen.

## Belegte Blocker

### 1. Queue-Persistenzfehler verliert lokale Absicht

Aktuell schreibt `saveTrades()`/`saveTradeHistory()` zuerst die lokale Projektion und `enqueueMutations()` entfernt das Item wieder, wenn das Schreiben von `aura-sync-pending-v1` fehlschlägt. Danach kann ein Pull Serverdaten einsetzen und die lokale Aktion rückgängig machen.

Muss-Verhalten:

1. Semantische Mutation zuerst dauerhaft stagen, bevor lokale Projektion als akzeptiert gilt.
2. Wenn Queue-LocalStorage nicht geschrieben werden kann:
   - Mutation nicht still verwerfen.
   - Keine falsche Anzeige `synchronisiert`.
   - Lokale Projektion entweder sauber auf den vorherigen Zustand zurückrollen oder gar nicht erst anwenden.
   - Bestehende Pending-Items niemals löschen.
   - UI klar `nicht synchronisiert`.
3. Promise-Fehler dürfen intern gefangen werden, aber Zustand und UI müssen fail-closed bleiben.
4. Auch atomischer Close/Partial-Close (Active + History) muss diese Reihenfolge einhalten.

Bevorzugte Struktur: eine einzige SyncEngine-Methode übernimmt synchron `stage durable intent -> apply local projection -> start queue`. Keine zwei unabhängigen, nicht-atomaren Helferketten.

### 2. Stale GET überschreibt bestätigten POST

Ein vor einem erfolgreichen POST gestarteter GET kann später mit alter Revision eintreffen und die bestätigte lokale Projektion überschreiben.

Muss-Verhalten:

1. `rev` ist streng monoton und darf nie sinken.
2. GET-Antwort mit `_rev < this.rev` vollständig als stale ignorieren: keine lokale Projektion, kein Shadow-Update, kein Status `synced`.
3. Zusätzlich Pull-Generation/Mutation-Generation verwenden, falls nötig, damit ein vor Queue-ACK gestarteter Pull nach ACK nicht mehr applyen darf.
4. Ein neuer GET mit gleicher/aktueller Revision darf normal angewendet werden, sofern kein Pending-Key geschützt werden muss.
5. Test mit deferred Promise: GET startet bei Rev 1, POST bestätigt Rev 2, dann GET Rev 1 resolved; lokaler Trade bleibt erhalten und rev bleibt 2.

### 3. Aktive FVG wird nach acht Zonen entfernt

`Symbiose_Dashboard.html` entfernt aktuell bei `zones.length > 8` die älteste Zone. Das kann eine noch unmitigierte Zone löschen.

Muss-Verhalten:

1. Keine aktive Zone wegen `zones.length` entfernen.
2. Falls Speicher begrenzt wird, nur bereits mitigierte/abgeschlossene Zonen komprimieren. Aktive Zonen vollständig behalten.
3. Test mit mindestens 9 unmitigierten FVGs: älteste aktive Zone existiert weiter und endet erst bei eigener vollständiger Mitigation.
4. JS/Pine-Semantik weiter angleichen. Pine verwaltet jede aktive Zone unabhängig; Plattform-Hardlimits ehrlich behandeln, aber keine willkürliche 8er-Lebensdauer einführen.

### 4. Beschädigte Server-State-Datei wird bei Legacy-Write überschrieben

`bitget_relay._save_shared_state()` schluckt JSON-Parsefehler und setzt `{}`. Der folgende Write überschreibt die beschädigte Datei.

Muss-Verhalten:

1. Existiert `STATE_FILE`, ist aber nicht als JSON-Objekt lesbar, Legacy-Write fail-closed abbrechen.
2. HTTP 500 `ERR_STATE_PERSIST`, keine 409.
3. Originaldatei bytegenau unverändert lassen.
4. Mutation- und Legacy-Pfad gleiche sichere Semantik.
5. Regressionstest mit invalidem JSON und anschließendem Legacy-POST.

### 5. Persistierte Queue-Länge beim Restore ungeprüft

`restoreQueue()` lädt beliebig viele Items.

Muss-Verhalten:

1. Vor dem Laden `stored.length <= maxQueueItems` verlangen.
2. Bei Overflow:
   - keine Items senden,
   - `queueOverflow = true`,
   - UI `nicht synchronisiert`,
   - Rohdaten nicht still löschen oder überschreiben.
3. Keine Busy-Loop.
4. Regressionstest mit `maxQueueItems + 1` serialisierbaren Items.
