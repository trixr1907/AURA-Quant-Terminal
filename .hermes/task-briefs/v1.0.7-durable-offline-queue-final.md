## Belegte Restursachen

### 1. Offline-Mutationen leben nur im RAM

`Symbiose_Dashboard.html` hält `SyncEngine.pending` nur als Array im aktuellen JS-Kontext. Wenn ein Upsert/Delete offline oder nach ausgeschöpften Retries noch unbestätigt ist und Seite/App neu startet, ist diese lokale Absicht weg. Der folgende Pull übernimmt Serverzustand und kann eine offline gelöschte Position wiederherstellen.

### 2. Release-Gate akzeptiert WARN als GO

`scripts/release_check.py::compute_verdict()` erlaubt `PASS` und `WARN`. Für den jetzt geforderten vollständig fail-closed Release-Vertrag darf exakt nur eine nichtleere Liste aus ausschließlich `PASS` zu `GO` führen. Report-only Hygiene darf deshalb entweder als nicht-verdict-relevante separate Information außerhalb `results` erscheinen oder muss als PASS mit informativem Detail modelliert werden. Kein WARN darf in einem GO-Stamp stehen.

## Muss-Verhalten

### A. Dauerhafte Pending-Queue

1. Definiere einen versionierten LocalStorage-Key, z. B. `aura-sync-pending-v1`.
2. Persistiere nur serialisierbare semantische Arbeit:
   - Mutation-Batch: `{kind:'mutations', mutations:[...], attempts:N}`
   - Legacy-Write: `{kind:'legacy', key, value, attempts:N}`
   - Keine Promise-Funktionen (`resolve`, `reject`) serialisieren.
3. Jede Queue-Änderung muss atomar im LocalStorage gespiegelt werden:
   - enqueue
   - Retry-/attempts-Änderung
   - erfolgreiche Entfernung
   - blockiert/entblockt, sofern Status persistiert wird
4. Beim `SyncEngine.init()` Queue vor erstem Server-Pull laden.
5. Wiederhergestellte Arbeit darf erst mit einem aktuellen Server-`rev` abgesendet werden. Empfohlene Reihenfolge:
   - durable Queue laden
   - initialen GET-Pull durchführen
   - bei vorhandener Queue Serverstate nur als confirmed shadow/revision anwenden, Pending-Key aber lokal nicht überschreiben
   - Queue sequenziell abarbeiten
6. Offline-Delete muss Reload überleben:
   - Server enthält ID X.
   - Client hat X lokal und löscht offline.
   - Queue enthält Delete X dauerhaft.
   - Seite wird neu geladen.
   - Server liefert weiterhin X.
   - Lokale UI bleibt ohne X; Delete wird nach Netzrückkehr gesendet.
   - Nach ACK Queue leer und Server ohne X.
7. Gleiches Prinzip für Upsert, History und atomische Active+History-Batches.
8. Maximale Queuegröße begrenzen (vernünftiges Limit, z. B. 1000 Items oder Gesamtgröße). Bei Überschreitung fail-closed: bestehende unbestätigte Arbeit nicht still löschen; UI `nicht synchronisiert` und klarer Fehler.
9. Korrupter Queue-JSON darf App nicht crashen. Korrupte Daten gesichert ignorieren/entfernen, Status sichtbar unsynchronisiert/Fehler; keine Serverdaten mutieren.
10. Nach permanentem 409/Netzfehler bleibt Item inklusive Attempts dauerhaft erhalten. Ein späterer Reload oder expliziter neuer Pull darf erneut versuchen, aber ohne Busy-Loop.
11. Bestehende Promise-Rückgaben müssen für Aktionen in derselben Sitzung weiter funktionieren. Für wiederhergestellte Items ohne Promise-Callbacks sichere No-op Callbacks verwenden oder Queue-Daten und Laufzeit-Waiter sauber trennen.

### B. Striktes fail-closed Release-Gate

1. `compute_verdict()` gibt nur `GO`, wenn:
   - mindestens ein Check existiert und
   - jeder Checkstatus exakt `PASS` ist.
2. `WARN`, `CONDITIONAL`, `NO-GO`, `FAIL`, unbekannt oder fehlend => Nicht-GO und Exitcode != 0.
3. Aktuelle Workspace-Hygiene ist reine Information. Sie darf einen sauberen Release nicht blockieren, aber auch keinen `WARN`-Check in einem `GO`-Result erzeugen. Verschiebe sie in ein separates Summary-Feld wie `info`/`notes` oder mache den Check `PASS` mit Reportdetail, sofern Semantik klar bleibt.
4. Textausgabe muss WARN korrekt darstellen, falls andere zukünftige Checks WARN liefern.
5. `build_package.py` akzeptiert weiterhin nur exakt GO.

## TDD-Pflicht

### RED zuerst

Ergänze mindestens:

1. Browserkontext A mit Server-ID `offline-delete`; initial pull oder lokaler confirmed shadow.
2. Fetch/POST offline; lokale Löschung enqueue; assert persistierter Queue-Key enthält Delete.
3. Neuen VM-/Browserkontext B mit demselben LocalStorage-Inhalt simulieren.
4. Initialer GET liefert alte Server-ID; assert lokale ID wird nicht resurrected.
5. Netz wieder online; assert Delete POST, Queue-Key leer/entfernt, Zustand synchronisiert.
6. Offline-Upsert über Reload.
7. Atomischer Active-delete+History-upsert Batch über Reload bleibt ein Batch.
8. Korrupter persistierter Queue-JSON crasht nicht und sendet nichts.
9. Permanent 409 bleibt persistent und erzeugt keinen Endlosloop.
10. `compute_verdict([{status:'WARN'}]) != 'GO'` und `PASS+WARN != GO`.
11. Aktueller realer Release-Check bleibt bei nur echten PASS-Checks GO; Hygiene erscheint getrennt/informativ.

RED-Ausgaben dokumentieren, dann minimal implementieren.
