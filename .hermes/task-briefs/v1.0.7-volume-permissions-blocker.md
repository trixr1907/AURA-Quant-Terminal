## Reproduzierter Blocker

Aktuelles Image läuft als Non-Root-User `aura`. Alle Starter mounten ein Docker-Named-Volume nach `/var/lib/aura`, aber dieses Ziel existiert im Image nicht mit passenden Besitzrechten. Docker erzeugt das Mount-Ziel root-owned. Der Relay kann deshalb State nicht schreiben.

Echter Repro mit frisch gebautem Image:

```text
GET /api/state -> 200 {"ok":true,"data":{}}
POST /api/state -> 409 ERR_STATE_CONFLICT
Container-Log:
Failed to persist mutation batch: [Errno 13] Permission denied: '/var/lib/aura/aura_shared_state.tmp'
```

Der 409 ist zusätzlich semantisch falsch: Speicherausfall ist kein Revisionskonflikt.

## Ziel

1. `/var/lib/aura` im Image vor `USER aura` anlegen und dem User `aura:aura` geben, damit ein frisches Named Volume beim ersten Mount korrekte Besitzrechte übernimmt.
2. State-Persistenzfehler sauber von Revisionskonflikten unterscheiden. Ein I/O-/Permission-Fehler muss HTTP 500 mit eigenem stabilen Fehlercode (z. B. `ERR_STATE_PERSIST`) liefern, nicht 409.
3. Legacy-Key-Write und Mutation-Batch müssen dieselbe korrekte Fehlersemantik haben.
4. Sicherheitsmodell beibehalten: Prozess läuft weiterhin als Non-Root-User `aura`.

## Implementierungshinweis

Minimaler erwartbarer Dockerfile-Vertrag, sinngemäß vor `USER aura`:

```dockerfile
RUN mkdir -p /var/lib/aura && chown -R aura:aura /var/lib/aura
```

Prüfe real, ob Docker das Ownership bei einem leeren Named Volume übernimmt. Nicht nur statisch annehmen.

Für Relay-Fehler nicht bloß `None` für Konflikt und I/O verwenden. Rückgabevertrag oder Exception so gestalten, dass Handler exakt unterscheiden kann:

```text
stale expected_rev -> 409 ERR_STATE_CONFLICT
write/replace/mkdir failure -> 500 ERR_STATE_PERSIST
```

Keine internen Pfade oder Exception-Details an Browser leaken; Details nur Server-Log.
